# 快速执行失败目标重试

2026-10-23，覆盖命令执行、脚本执行、文件分发，以及快速执行历史详情。

## 使用方式

- 在“执行任务”弹窗或历史详情的失败/超时主机行点击“重试”，仅提交这一条结果 ID。
- “重试失败”按钮提交整批失败目标；已成功、执行中、已在子重试任务中成功的主机不会重复执行。
- 点击后创建关联原任务的独立重试任务，弹窗显示重试进度；原任务与成功结果继续保留在历史中。
- 重复点击会被前端拦截，后端也检查已创建的运行中/成功子任务。当前创建锁用于单后端进程；多实例部署需要共享锁及共享文件副本目录。

## 执行内容

- 命令：沿用原命令、参数、超时时间和并发数，重新检查当前命令过滤策略与主机执行权限。
- 脚本：新任务将原脚本内容、解释器、版本及已解析变量加密保存，重试不使用后来修改的脚本内容。重试仍检查脚本是否启用、当前过滤策略与主机权限。
- 文件：新任务在 `data/ops-retry/` 保存独立文件副本，沿用原目标路径及覆盖设置，不重新读取可能已变化的远程源文件。副本保留24小时，启动时和每小时清理过期副本，运行中任务占用的副本跳过清理；文件权限为0600、目录0700（Windows还受目录ACL控制）。重试任务各自拥有副本。
- 不要求用户重复确认原任务已批准的操作，但每次重试重新检查当前资源授权。文件目标检查上传权限。

## 接口与升级

`POST /api/v1/ops/exec/retry`

```json
{"taskId":123,"resultId":456}
```

`resultId` 为可选项；省略表示重试剩余失败目标。服务端只允许所给任务中的失败/超时结果。

`OpsExecTask` 新增持久字段 `retry_context`（加密，API不输出）、`file_retry_until`。现有 AutoMigrate 在后端启动时添加字段。虚拟响应字段 `retrySupported` 表示后端支持逐台重试，前端只在该字段为true时启用入口，避免旧后端忽略resultId后变成整批重试。

需要更新并重启后端才能启用新能力。本轮没有重启现有服务，以免中断用户正在使用的SSH会话或执行任务，也未提交、推送、部署。

升级前的文件任务已删除原上传文件，不能恢复丢失内容；需要重新上传。升级前脚本任务没有完整运行变量快照，会明确提示重新提交，避免以新脚本或默认变量冒充原执行内容。原命令任务可继续重试。
